# 아이템과 인벤토리 UI — 설계 스펙

_작성일: 2026-07-30 · 프로젝트: Defrag (pygame-ce)_

## 목표

코어를 **상자처럼** 쓸 수 있게 만든다. 코어 앞에서 키를 누르면 창이 열리고, 왼쪽에 코어의
내용물이, 오른쪽에 플레이어의 백팩이 파일 목록처럼 뜬다. 옮길 것을 끌어다 놓으면 전송이
시작되고, 양이 많을수록 오래 걸린다.

지금은 인벤토리에 **아이템이라는 것이 없다.** `Folder`는 파편 개수를 세는 정수 하나이고,
코어에 다가서면 백팩이 통째로 빨려 들어간다. 그래서는 끌어다 놓을 대상 자체가 없다. 이
스펙은 먼저 아이템에 종류와 정체성을 주고, 그 위에 창을 얹는다.

게임의 소재가 파일 시스템(`/Documents`, MB, 조각모음)이므로 UI는 상자 격자가 아니라
**파일 목록**이다. 한 줄에 아이콘 하나와 이름 하나. 이 은유가 게임 전체와 맞아떨어진다.

## 로드맵에서의 위치

| 스펙 | 내용 | 상태 |
|---|---|---|
| A. 코어 방어 | 코어 HP, 적 종류, 어그로, 수리, 패배 신호 | 설계 완료 |
| **E. 아이템 & 인벤토리 UI** (이 문서) | 아이템 모델, 코어 상자, 드래그 앤 드롭, 전송 딜레이 | 설계 중 |
| B. 보스 | 자원 임계치 → 소환 → 보스전 → 승리 신호 | 미착수 |
| C. 씬 흐름 | 타이틀 / 일시정지 / 승리 / 게임오버 | 미착수 |
| D. 세이브 | 슬롯 여러 개 | 미착수 |

E는 A와 독립적으로 설계됐지만 **먼저 구현하는 편이 낫다.** A의 수리, B의 보스 소환 비용,
D의 세이브가 모두 저장소를 읽고 쓴다. 아이템 모델을 먼저 확정하면 그 셋을 각각 한 번씩만
작성하면 된다. 반대 순서로 가면 A의 수리를 정수 카운트 기준으로 짰다가 E에서 다시 고치게
된다.

## 범위 (포함 / 제외)

**포함:** 아이템 종류 카탈로그, 슬롯 없는 목록형 저장소(`Folder` 개편), 코어 인벤토리 창,
좌우 두 패널, 드래그 앤 드롭(전량 / 절반 / 1개), 수량에 비례하는 전송 딜레이와 진행 표시,
창이 열려 있어도 계속 도는 월드, 새 로직 전부의 단위 테스트.

**제외:** 파편 외의 실제 아이템 종류(구조만 만들고 행은 나중에 추가), 정렬·검색·필터,
아이템 툴팁, 창 크기 조절, 게임패드 조작, 세이브(D 스펙).

## 아이템 모델

### `items/item_kinds.py` (신규) — `ItemKind` (frozen dataclass)

`EnemyKind`와 같은 패턴이다. 데이터는 테이블에, 행동은 시스템에.

```
key: str                     # 저장·비교용 안정 식별자
name: str                    # 목록에 보이는 이름
mb: int                      # 1개당 용량
color: tuple[int, int, int]  # 목록 아이콘 색
```

지금 정의하는 행은 **파편 하나뿐**이다.

| key | 이름 | MB | 비고 |
|---|---|---|---|
| `fragment` | 데이터 조각 | 3 | 채굴로 얻는 유일한 자원 |

종류를 늘리는 건 행을 추가하는 일로 끝난다. 지금 없는 종류를 미리 만들지 않는 이유는,
무엇이 필요한지는 보스(B)와 업그레이드를 설계할 때 정해지기 때문이다.

`key`와 `name`을 나눈 건 세이브(D) 때문이다. 저장 파일에는 `key`가 들어가므로 표시 이름을
바꿔도 기존 세이브가 깨지지 않는다.

### `inventory/storage.py` — `Folder` 개편

칸이 아니라 **줄의 목록**이다. 같은 종류는 한 줄로 묶이고 개수를 갖는다.

```
cap_mb: int
items: dict[str, int]        # ItemKind.key -> 개수
reserved_mb: int             # 전송이 들어오기로 예약해 둔 공간 (아래 참조)
```

- `used_mb` — 담긴 것들의 MB 합
- `free_mb` — `cap_mb - used_mb - reserved_mb`
- `fits(kind, n) -> int` — 지금 실제로 들어갈 수 있는 개수 (요청한 `n` 이하)
- `add(kind, n) -> int` / `remove(kind, n) -> int` — 넣거나 빼되 경계에서 잘리고, 실제
  처리된 개수를 돌려준다 (지금 `Folder`의 계약을 그대로 이어받는다)
- `count(kind) -> int`
- `rows()` — 화면에 그릴 순서대로 `(ItemKind, 개수)` 목록. 개수가 0인 종류는 빠진다.
  빈 폴더는 빈 목록이다.

`is_full`은 없어진다. 종류마다 크기가 다르면 "가득 참"은 종류를 빼고 말할 수 없다.
채굴이 백팩을 막던 `backpack.is_full` 판정은 `backpack.fits(FRAGMENT, 1) == 0`이 된다.

카탈로그는 `ITEM_KINDS: dict[str, ItemKind]`(키로 찾기)와 `CATALOGUE: tuple[ItemKind, ...]`
(그리는 순서) 두 형태로 노출한다.

**용량은 계속 MB로 제한한다.** 칸 수가 아니다. 아이템마다 크기가 다를 수 있어서 "이건 무거우니
둘만 들고 간다" 같은 판단이 생기고, 저장장치라는 소재와도 맞으며, 지금의 용량 계산과 HUD
게이지를 거의 그대로 쓸 수 있다.

### 바뀐 용량 수치

| 값 | 이전 | 이후 |
|---|---|---|
| 파편 1개 | 5 MB | **3 MB** |
| 백팩 | 50 MB (10개) | **100 MB (33개)** |
| 코어 저장고 | 500 MB (100개) | **750 MB (250개)** |

이 세 숫자는 이미 `config.py`에 반영했다. 이로 인해 스펙 A의 수리 비용이 저장고의 80 %에서
약 3분의 1로 가벼워졌고, A 문서에도 반영했다.

### 정렬 순서

목록은 **카탈로그에 정의된 순서**로 그린다. 개수나 이름으로 정렬하지 않는다. 줄이 옮길
때마다 자리를 바꾸면 드래그 목표가 손 밑에서 움직여서 조작이 어긋난다. 고정된 순서면
"두 번째 줄이 파편"이라는 위치 기억이 유지된다.

## 인벤토리 창

### 여는 법

코어 동기화 범위 안에서 **`E`**. 다시 누르거나 `ESC`로 닫는다. 범위를 벗어나면 자동으로
닫힌다 — 창을 열어둔 채 걸어 나가서 원격으로 짐을 옮기는 걸 막는다.

창이 열려 있으면 `ESC`는 **창만 닫는다.** 지금처럼 씬을 pop해서 게임을 나가면 안 된다.

지금 `E`는 백팩을 즉시 전량 전송하는 키인데, 그 동작은 이 창으로 대체된다.

**플레이어가 죽으면 창은 닫힌다.** 죽은 동안에는 조작 대상이 없고, 사망 페널티가 백팩을
반으로 줄이는데 그 장면을 창에 띄워둘 이유가 없다. 진행 중인 전송은 그대로 간다.

참고: 창이 열린 동안 이동이 막히므로 "범위를 벗어나서 자동으로 닫히는" 경우는 **지금은
일어나지 않는다.** 나중에 넉백이나 강제 이동이 생겼을 때를 위한 한 줄짜리 보험이다.

### 배치

```
┌─────────────────────────┬─────────────────────────┐
│  코어 (/Documents)      │  백팩                   │
│  123 / 750 MB           │  27 / 100 MB            │
├─────────────────────────┼─────────────────────────┤
│  ■  데이터 조각    ×41  │  ■  데이터 조각    ×9   │
│                         │                         │
│                         │                         │
├─────────────────────────┴─────────────────────────┤
│  전송 중: 데이터 조각 ×12   ▓▓▓▓▓▓░░░░  3.1초     │
└───────────────────────────────────────────────────┘
```

왼쪽이 코어, 오른쪽이 백팩. 각 줄은 왼쪽에 색 아이콘, 오른쪽에 이름과 개수. 패널 머리에는
용량이 뜬다. 아래쪽 띠는 진행 중인 전송을 보여준다.

### 드래그 앤 드롭

한 줄을 집어 반대편 패널에 놓으면 전송이 걸린다. 집는 양은 보조키로 정한다.

| 조작 | 옮기는 양 |
|---|---|
| 드래그 | 그 줄 전부 |
| `Shift` + 드래그 | 절반 (올림) |
| `Ctrl` + 드래그 | 1개 |

받는 쪽 용량이 모자라면 **들어갈 만큼만** 옮기고 나머지는 보내는 쪽에 남는다. 거절하지
않고 부분 수용하는 건 지금 `Folder.add`가 이미 그렇게 동작하기 때문이고, 꽉 찬 저장고
앞에서 아무 일도 안 일어나는 것보다 낫다. 이 판정은 놓는 순간 한 번만 한다.

드래그 중에는 집은 것이 커서를 따라다닌다. 패널 밖에 놓으면 취소다.

## 전송 딜레이

### 규칙

드래그를 놓는 순간 세 가지가 한꺼번에 일어난다.

1. 옮길 개수를 **받는 쪽에 지금 들어가는 만큼으로 자른다** (`dst.fits(kind, n)`).
2. 그만큼의 MB를 받는 쪽에 **예약**하고(`reserved_mb` 증가), 보내는 쪽에서 **즉시 뺀다.**
3. 작업(job)이 만들어진다. 끝나면 예약을 풀고 받는 쪽에 넣는다.

그 사이 아이템은 어느 쪽에도 없다. 보내는 쪽에서 먼저 빼는 이유는 **복제를 막기**
위해서다 — 먼저 넣고 나중에 빼면 그 사이에 개수가 두 배로 보이는 순간이 생긴다.

예약이 필요한 이유는 그 반대편 사고 때문이다. 예약이 없으면 코어→백팩 전송을 걸어두고
창을 닫은 뒤 채굴로 백팩을 채웠을 때, 작업이 끝나는 순간 물건이 갈 곳이 없어 **사라진다.**
예약을 `Folder`에 두면 채굴이든 다른 전송이든 그 공간을 건드리지 못한다. 큐에 두면
채굴 코드가 큐를 모르므로 또 뚫린다.

따라서 **작업은 완료 시점에 반드시 전량 들어간다.** 부분 수용은 놓는 순간 한 번만
일어난다.

소요 시간은 `TRANSFER_TIME_PER_MB` × 옮기는 총 MB다. 개수가 아니라 MB에 비례시키는 건,
나중에 무거운 아이템이 생겼을 때 "큰 파일이 오래 걸린다"가 저절로 성립하기 때문이다.

`TRANSFER_TIME_PER_MB = 0.02초` — 파편 하나(3 MB)에 0.06초, 백팩을 꽉 채운 33개(99 MB)에
약 2초.

### 큐

작업은 **한 번에 하나만** 진행되고 나머지는 줄을 선다. 여러 개가 동시에 조금씩 진행되면
진행 표시가 읽히지 않고, 순서대로 처리하면 화면에 보여줄 것도 한 줄이면 된다.

### 창을 닫아도 계속 간다

세계가 계속 도는 것과 같은 이유로 전송도 계속 진행된다. 창을 닫고 싸우러 나가도 짐은
옮겨진다. 창을 닫는 것이 전송을 취소하는 수단이 되면, 잘못 놓았을 때 창을 닫는 것으로
무를 수 있게 되어 딜레이가 무의미해진다.

**코어 범위를 벗어나도 진행 중인 작업은 끝까지 간다.** 이미 보내는 쪽에서 빠져나온 물건이라
중간에 멈추면 갈 곳이 없다.

### 왜 딜레이가 긴장을 만드는가

창이 열려 있어도 세계는 돈다. 코어 근처는 스펙 A에서 자폭 유탄이 터지는 곳이 됐다. 큰 짐을
부리려면 그만큼 오래 그 자리에 머물러야 하므로, **"한 번에 다 옮길까, 나눠서 옮길까"**가
실제 판단이 된다. 딜레이는 불편함이 아니라 이 선택을 만들기 위해 존재한다.

## 씬 구조

여기서 기존 구조의 한계를 하나 건드린다. `SceneManager`는 스택이지만 `update` · `draw` ·
`handle_event`를 **맨 위 씬에만** 위임한다. 인벤토리 창을 별도 씬으로 push하면 뒤의 게임이
그려지지 않는다.

이 스펙에서는 **씬을 새로 만들지 않는다.** 창은 `PlayScene`이 소유하는 오버레이 상태
(`self.inventory_open`)이고, 입력은 `PlayScene.handle_event`가 창이 열려 있을 때 먼저
가로챈다. 이유는 두 가지다. 첫째, 세계가 계속 돌아야 하므로 별도 씬으로 분리해서 얻을 게
없다. 둘째, `SceneManager`를 고치는 일은 일시정지 화면이 실제로 필요해지는 스펙 C의 몫이고,
거기서 제대로 설계하는 편이 낫다.

창이 열려 있는 동안 플레이어 조작(이동·채굴·발사·회피)은 막힌다. 마우스가 UI에 묶여 있는데
클릭이 총으로 나가면 안 된다. 다만 **월드는 계속 돌고 적은 계속 다가온다.**

## 파일 배치

| 파일 | 변경 |
|---|---|
| `items/item_kinds.py` | **신규** — `ItemKind` + 카탈로그(파편 1행) |
| `inventory/storage.py` | `Folder`를 `dict[key, 개수]` 기반으로 개편, `transfer` 제거 |
| `inventory/transfer.py` | **신규** — `TransferJob`, 큐, `update(dt)` |
| `ui/inventory_panel.py` | **신규** — 목록 그리기, 히트 테스트, 드래그 상태 |
| `scenes/play.py` | 창 열고 닫기, 입력 가로채기, 전송 큐 갱신, 오버레이 그리기 |
| `entities/fragment.py` | `mb_value` 대신 `ItemKind` 참조 |
| `systems/mining.py` | `backpack.add(1)` → `backpack.add(FRAGMENT, 1)` |
| `config.py` | 전송 속도, 창 배치 수치 |

`ui/`는 새 패키지다. 지금까지는 모든 그리기가 씬 안에 있었지만, 목록 배치·히트 테스트·드래그
상태는 씬에 두기엔 덩치가 크고 씬과 무관하게 테스트할 수 있다. `systems/`가 아니라 `ui/`인
건 화면 좌표를 다루기 때문이다.

## 기존 코드에 생기는 파장

- `Folder`의 계약이 통째로 바뀐다. `count`(정수)를 읽던 곳이 전부 `count(kind)`로 바뀐다 —
  `mining.py`, `combat.apply_death_penalty`, `play.py`의 HUD 게이지, 그리고 테스트 여러 곳.
  HUD의 백팩 게이지는 `used_mb / cap_mb`라 그대로 쓴다.
- `is_full`이 없어지므로 `mining.py`의 만적 판정이 `fits(FRAGMENT, 1) == 0`으로 바뀐다.
- **사망 페널티가 종류별로 계산된다.** "백팩의 절반을 떨어뜨린다"는 이제 각 줄마다 절반을
  떨어뜨리는 것(올림해서 남김)으로 정의한다. 종류가 하나뿐인 지금은 기존과 결과가 같고,
  종류가 늘어도 "비싼 것만 살아남는다" 같은 편법이 안 생긴다. 예약된 공간은 건드리지
  않는다 — 이미 백팩에 없는 물건이다.
- `transfer(src, dst)` 함수는 사라진다. 전송은 이제 큐를 거친다.
- `E` 키의 의미가 "즉시 전량 전송"에서 "창 열기"로 바뀐다. 방금 추가한 동기화 테스트 네 개는
  창 열기 테스트로 대체된다.
- `Fragment.mb_value`가 `ItemKind` 참조로 바뀐다.
- 스펙 A의 수리는 `documents.remove(FRAGMENT, n)`을 쓰게 된다. A를 나중에 구현하면 이
  변경은 저절로 반영된다.

## 테스트

**아이템 모델** — 용량이 MB 합으로 계산된다 / 용량을 넘겨 넣으면 들어갈 만큼만 들어가고
실제 개수를 돌려준다 / 없는 걸 빼면 0을 돌려준다 / 종류별로 개수가 따로 센다 / 목록 순서가
카탈로그 순서와 같고 개수가 바뀌어도 순서가 유지된다 / 개수가 0인 줄은 목록에 없다 /
예약된 공간은 `free_mb`와 `fits`에서 빠진다.

**전송 작업** — 놓는 즉시 보내는 쪽에서 빠진다 / 시간이 다 지나야 받는 쪽에 들어간다 /
진행 중에는 어느 쪽에도 없다 / 소요 시간이 총 MB에 비례한다 / 작업이 순서대로 하나씩
처리된다 / 받는 쪽이 가득 차 있으면 놓는 순간 들어갈 만큼으로 잘린다 / **작업이 걸린
동안에는 채굴이 그 예약 공간을 못 쓰고, 완료 시 전량이 들어간다** (아이템 소멸 방지) /
예약 공간이 없으면 아무 작업도 안 만들어진다.

**창** — 코어 범위 안에서 `E`로 열린다 / 범위 밖에서는 안 열린다 / 범위를 벗어나면 닫힌다 /
닫아도 진행 중인 작업은 계속된다 / 열려 있는 동안 플레이어 이동·발사 입력이 막힌다 /
열려 있어도 적과 스포너는 계속 갱신된다 / 열려 있을 때 `ESC`는 씬을 pop하지 않고 창만
닫는다 / 사망 시 창이 닫힌다.

**드래그** — 기본은 전량, `Shift`는 절반(올림), `Ctrl`은 1개 / 패널 밖에 놓으면 취소되고
아무것도 옮겨지지 않는다 / 같은 패널 안에 놓으면 아무 일도 없다.

드래그 판정과 목록 배치는 화면 좌표를 다루지만 **순수 함수로 뽑아서 표면 없이 테스트한다**.
"이 좌표가 몇 번째 줄인가"는 `pygame.Surface` 없이 계산할 수 있다. 실제 그리기는 늘 하던
대로 "예외 없이 그려진다"까지만 본다.

## 숫자는 첫 값이다

`TRANSFER_TIME_PER_MB`가 이 스펙에서 가장 자신 없는 값이다. 너무 짧으면 딜레이가 있으나
마나이고, 너무 길면 짐 부리는 것이 지루한 대기가 된다. 백팩을 꽉 채워 옮기는 데 2초 정도가
적당해 보이지만 실제로 코어 앞에서 적을 상대해봐야 안다.
